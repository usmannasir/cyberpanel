# Separate application identities for fresh remote MySQL installations

Remote MySQL has two connections: the supplied administrative/bootstrap account (`--mysqluser`, `ROOT_DB_USER`) and CyberPanel's application account (`DB_USER`). A custom bootstrap username has always selected the administrative connection; it does not select the application user.

Fresh installations may now opt into a distinct application database and user:

```
export CP_INSTALL_APP_DB=panel_vm201
export CP_INSTALL_APP_USER=panel_vm201_app
# Run the normal downloaded installer and select Remote MySQL.
```

For direct `install.py` callers, use `--appdb panel_vm201 --appuser panel_vm201_app` with the existing remote endpoint/bootstrap options. Supply the bootstrap password through `CP_INSTALL_MYSQL_PASSWORD`, not a command-line argument. The application password is generated by the installer and is not logged. Omitting both application options preserves the historical `cyberpanel` database/user defaults.

Both custom names are required. They must start with an ASCII letter and contain only letters, digits, and underscores; database length is at most 64 and username at most 32. System/default names and reuse of the bootstrap username are rejected. Custom identities are only supported with remote MySQL. The account grant uses the client host observed by the selected database server. This does not change routing or configure database TLS/network access.

An existing `/etc/cyberpanel/mysqlPassword` or panel `.env` also blocks this opt-in before installer mutations; an established panel cannot be silently repointed. A custom database or username must be unused. An existing schema or account at any host causes a refusal before any CREATE/ALTER/GRANT statement. There is no automatic takeover, password reset, rename, or conversion of existing installations. If an interrupted custom installation already created its objects, investigate and preserve its data before retrying; the installer deliberately refuses to adopt them. DDL is not transactional: a later database error may leave newly created objects for an administrator to inspect.

The administrative connection needs permission to inspect `mysql.user`, create the requested database/account, and grant the application's privileges. It remains configured for CyberPanel's database-management operations. Separate application identities do **not** isolate panels from a shared privileged bootstrap account; provision and secure each administrative account according to the intended management boundary.

The selected application identity reaches Django `.env`/fallback settings, DNS, FTP, Postfix and Dovecot configuration. Their reset writers preserve the configured identity. Ordinary upgrades preserve `.env` and the loaded `DATABASES` configuration. If remote settings cannot be imported, upgrade recovery stops rather than creating/resetting a local `cyberpanel` account. Restoring settings is required; this feature does not migrate an existing database or change its grants.

Database-level GRANT patterns escape underscores when MySQL/MariaDB treat them as wildcards. With MySQL `partial_revokes` enabled, literal names are used. This prevents `panel_a` from also granting access to a schema named `panelXa`. See the [MySQL GRANT reference](https://dev.mysql.com/doc/refman/8.0/en/grant.html).

## Verification

Unit tests execute the installer and reset configuration writers in temporary directories, cover validation/collision rejection and the actual upgrade state/credential merge. Real MySQL 8.0 integration tests provision two distinct identities, render `.env`, execute the shipped Django `DATABASES` expression, run Django auth/contenttypes migrations, write/read each panel's data, reject cross-schema reads/writes/drops, and verify collision refusals preserve old passwords and data. The tests run with `partial_revokes` both disabled and enabled. These are not a full CyberPanel installation, all-application migration, live mail/DNS/FTP daemon, customer-host, or MariaDB integration certification.

```
PYTHONPATH=.:install python3 -m unittest install.test_application_identity install.test_application_identity_reset
# Disposable server only; use CP_TEST_MYSQL_* as documented by the existing suite:
PYTHONPATH=.:install python3 -m unittest install.test_application_identity_integration
```
