# ASN-based request filtering with OpenLiteSpeed

This is a tested server-side alternative for issue #1711. It uses OpenLiteSpeed's MaxMind lookup and rewrite rules. It does not add an ASN variable to ModSecurity or generate a ModSecurity audit event. An ASN value available to PHP is not automatically available to ModSecurity.

## Configure the trusted lookup

Use an administrator-maintained, current GeoLite2-ASN or GeoIP2-ASN database obtained through your authorized MaxMind account. Keep its existing licensing and update requirements. The web-server user needs read access; website tenants must not be able to replace it.

For a directly exposed origin, set **Use Client IP in Header** to **No** (`useIpInProxyHeader 0`) in OpenLiteSpeed's server configuration. The tests below use the actual TCP peer address. If the server is behind a CDN or reverse proxy, first configure and verify its restricted trusted-proxy policy; selecting arbitrary forwarded headers would make an ASN rule bypassable. Setting direct-peer mode behind a proxy classifies the proxy's ASN, not the visitor's.

Add the database through WebAdmin's IP-to-Geo configuration, or merge this block into the existing server configuration without replacing other settings:

```
enableIpGeo 1
geoipdb /usr/local/share/GeoIP/GeoLite2-ASN.mmdb {
  geoipDBName ASN_DB
  maxMindDBEnv GEOIP_ASN ASN_DB/autonomous_system_number
}
```

Use the exact `GEOIP_ASN` name in both places below. This name worked in the native acceptance test; an arbitrary custom name without the GeoIP prefix did not work in the rewrite lookup.

## Apply the website rule

In the selected website's existing rewrite rules, add:

```
RewriteCond %{ENV:GEOIP_ASN} ^(64500|64501)$
RewriteRule ^ - [F,L]
```

`64500` and `64501` are synthetic example ASNs. Replace them with the ASNs your policy actually intends to deny. The anchored numeric match prevents partial matches. This returns HTTP 403 for matching ASNs and leaves other website rules in place.

The basic denylist permits addresses with no lookup result. That also means a database-loading failure can allow requests that would otherwise match. If your policy must reject all unknown lookups, place this explicit rule before the denylist:

```
RewriteCond %{ENV:GEOIP_ASN} ^$
RewriteRule ^ - [R=503,L]
```

This stricter variant returns HTTP 503 for unknown addresses and database failures. It can also affect private-network clients and health checks. Select that behavior deliberately.

Back up the affected configuration, validate it with `/usr/local/lsws/bin/openlitespeed -t`, and review errors before applying the configuration. This build uses status 0 for clean, 1 for warnings, and 2 for errors. Database checks and real requests are also required: a successful syntax check alone is insufficient to prove the lookup is active. After a controlled reload, test known allowed/denied clients over both IP families and check the OLS error log for `[GEO]` errors. A bad update should be replaced with the prior known-good database and configuration, then revalidated. Update database files atomically rather than truncating an active memory-mapped file.

## Verified behavior and limits

Native acceptance used an isolated Ubuntu 22.04.5 x86_64 container, the published CyberPanel OLS core SHA256 `736eeb47bd3dc7b2a7206b95106dd735a80b3386118d0b4b17f39f9fa5324f8c`, and a synthetic MMDB generated by MaxMind's official writer. No customer system, production binary, license check, paid feature, or entitlement was changed.

| Case | Basic denylist | Strict unknown policy |
| --- | --- | --- |
| Denied ASN, IPv4/IPv6 | 403 | 403 |
| Allowed ASN, IPv4/IPv6 | 200 | 200 |
| Unknown address, IPv4/IPv6 | 200 | 503 |
| Missing/corrupt database after reload, IPv4/IPv6 | 200 | 503 |

With direct-peer mode explicitly configured, spoofed ASN, X-Forwarded-For, and CF-Connecting-IP headers could not turn the tested denied source into an allowed one. Missing/corrupt databases produced configuration errors. The tests deliberately reloaded failed fixtures to establish runtime failure behavior; do not do that on a production server.

No MMDB-to-ModSecurity ASN integration is claimed. If a rule specifically needs ASN inside ModSecurity, that capability remains outstanding. The example is for request blocking in OLS. It does not validate a particular production MaxMind dataset, trusted-proxy deployment, Enterprise LiteSpeed installation, or every older OLS release.

Reproducible isolated test assets are in `tests/native/asn_filter/`. Never use the synthetic test database as production geolocation data.

References: [OpenLiteSpeed geolocation and rewrite variables](https://docs.openlitespeed.org/config/advanced/geolocation/), [libModSecurity 3.0.17 geographic extraction](https://github.com/owasp-modsecurity/ModSecurity/blob/v3.0.17/src/utils/geo_lookup.cc), and [MaxMind's MMDB writer](https://github.com/maxmind/mmdbwriter).
